### 4.3 Thin pool, no borrowed question

**Proposal.** A start needs, per blueprint slot kind, at least as many distinct eligible items as slots of that kind (15 and 10 today, read from the blueprint, not hard-coded). If either pool is short, the start returns `pool_insufficient`, creates no attempt and shows one generic Bulgarian "not enough questions yet" message with no counts and no source names. It never fills a slot from: a non-DZI or AI-generated question, a Part 2 item, an unlinked legacy item, an item on the stimulus-missing list, an item of the other kind, another subject, or a repeated question. An open attempt keeps its stored plan and slot format (§6.2). Each point is a test (§9).

## 5. Runtime storage

### 5.1 Constraints from the current code (Fact)

- `quiz_attempts.assignment_id` is `NOT NULL` (`web/migrations/001_quiz_tables.sql:14`) and unique per `(assignment_id, user_id)` (`015_quiz_attempts_user.sql:58`); `quiz_text_answers.attempt_id` references `quiz_attempts` with cascade (`005_quiz_text_answers.sql:24`), as do `quiz_answers` (`001_quiz_tables.sql:27`) and `practical_submissions` (`008_practical_submissions.sql:12`). Short answers cannot be stored without an attempt row.
- A new assignment needs a teacher or admin principal and the creation quota (`web/services/quiz.py:268-297`; `docs/STUDENT_PRACTICE_DESIGN.md` §2).
- C2 tables are section/topic scoped and multiple-choice only: `practice_sessions.section_id NOT NULL`, `score_total > 0`, the open-scope index over `(user_id, section_id, COALESCE(topic_id, 0))`; `practice_answers` stores a letter and a verdict (`web/migrations/026_practice_runtime.sql:32-95`). `_resolve_scope` rejects `dzi_training` sections and `_eligible_question_ids` excludes DZI rows (`web/services/practice.py:548-583`).
- No existing table has a deadline for an attempt. `assignment.time_limit_minutes` is advisory: the server computes remaining time for display and the client timer only ever allows an *empty* submission; the cutoff that binds is the assignment lifecycle (`web/blueprints/quiz.py:183-199`, `web/services/quiz.py:1775-1785`). The existing token-landing and attempt `GET` handlers can write lifecycle observation markers (`web/blueprints/quiz.py:96,234`); C3 must not.

**E. One table with an answers JSON column** is the smallest in table count and was considered. It is not recommended: the updater's reference gate reads every integer in a registered JSON column as a question id, and the parity check reads list items and `id`-like keys (§5.4), so an answers document with letters, points and slot numbers would be read differently by the two and would need either a bespoke walker or a flat shape that is no longer an answer document; RESTRICT keys and `CHECK`s cannot protect ids or points inside JSON; and per-question reads for C4 would parse JSON. D keeps ids in integer columns the existing gate already understands.

D is the smallest change that keeps the three existing contracts intact. The cost is one more pair of tables and a result page of its own; that is accepted.

### 5.3 Proposed shape (migration `027_dzi_part1_runtime.sql`, not written here)

`dzi_part1_attempts`:

- `id` (positive); `user_id` NOT NULL, RESTRICT to `users`; `blueprint_id` NOT NULL, RESTRICT to `dzi_blueprints` (provenance only: nothing reads the blueprint's slots after start); `seed` text.
- `question_ids_json` text: a **flat array of 25 distinct positive question ids in slot order, slot = position + 1**, and nothing else.
- `slot_format_json` text: an array of 25 objects `{"kind": "multiple_choice" | "short_answer", "points": <positive integer>}` in slot order, copied at start from the blueprint slots that start validated, and never rewritten. It holds no question id, so it is registered in **neither** `JSON_ID_COLUMNS` nor the parity check (§5.4); `question_ids_json` stays flat.
- `max_points_planned` integer (the sum of the snapshot points: 45 today); `duration_seconds` integer > 0.
- `started_at`, `deadline_at`, `submit_cutoff_at`: NOT NULL text in the lifecycle format (`web/services/lifecycle.py:180`). Written once, in the start transaction, from the one `now` of that transaction: `deadline_at = started_at + duration_seconds`, `submit_cutoff_at = deadline_at + SUBMIT_GRACE_SECONDS`. No later statement updates them. Every state decision reads the stored `submit_cutoff_at`; the constant is read only to compute it for a new attempt, so changing it cannot revive or kill a row already stored (§7.2).
- Nullable `submitted_at`, `expired_at`, `abandoned_at` (at most one set); `score_points`, `score_max` set iff submitted, `0 <= points <= max`, `max > 0`.

A partial unique index on `(user_id)` while all three terminal timestamps are null gives one open attempt per account; an index on `(user_id, started_at)` serves later reads.

Row-local `CHECK`s (**Proposal**, in the 026 style: `web/migrations/026_practice_runtime.sql:32-95`): types and ranges; the six timestamp columns match the fixed-width `YYYY-MM-DD HH:MM:SS` shape (026 only tests `typeof`, but the orderings below compare text, which equals time order only for that shape); `started_at < deadline_at AND deadline_at < submit_cutoff_at`; at most one terminal timestamp; if `submitted_at` is set, `started_at <= submitted_at < submit_cutoff_at`; if `expired_at` is set, `expired_at >= submit_cutoff_at`. The last two hold because the service refuses a submit before `started_at` or at or after the cutoff, and marks expiry only at or after the cutoff (§6.4, §7.2). `abandoned_at` has **no** ordering `CHECK`: a row stamped later than lifecycle `now` is marked abandoned, by a start or by `clock-recover`, at a time earlier than its `started_at` (§7.4). What the schema does **not** implement, and the service and its tests must: that `deadline_at` and the cutoff follow the arithmetic above, the shape of both JSON columns, the slot count, who may start, read or submit, eligibility, scoring and state transitions.

`dzi_part1_answers`: primary key `(attempt_id, slot_number, subquestion_number)`; `attempt_id` RESTRICT to the attempt; `question_id` RESTRICT to `questions`; `kind` in (`multiple_choice`, `short_answer`); `subquestion_number` 0 for multiple choice, 1 or more for short answer; `chosen_letter` (multiple choice only, the stored option key); `raw_answer` (short answer only, text); `is_correct` 0 or 1; `points_possible`, `points_awarded` whole numbers with awarded 0 or possible; `grader_version` text. Row-local `CHECK`s only (kind-consistent columns, types, ranges), as in 026. **Where the values come from (service, not table).** `kind` and the slot total come from `slot_format_json`. `points_possible` is the slot's points for a multiple-choice row and the **stored part weight** (`fill_in_subquestions.points`) for a short-answer row (§6.5); the part weights of one slot sum to that slot's stored points, which the service checks when it composes the pool (§4.1) and again when it grades (§6.4 step 6). **`raw_answer` carries no length `CHECK`**: its bound is enforced by the service (§6.4), so changing the bound later needs no table rebuild. No question text, no accepted answer, no blob, no name, no timestamp from a client.

**Uniqueness, stated accurately.** The primary key makes each `(slot, part)` unique within an attempt. A second unique key `(attempt_id, question_id, subquestion_number)` prevents only a duplicate of the **same question part**. It does **not** keep a question out of two slots: the table accepts `(slot 16, Q, part 1)` together with `(slot 17, Q, part 2)`. That guarantee is a **service invariant**: the stored plan holds 25 distinct ids, and every row the service writes has `question_id` equal to the plan entry for its `slot_number`, `kind` equal to that slot's `slot_format_json` entry, `points_possible` equal to its points (multiple choice) or to a stored part weight (short answer), and a `subquestion_number` that is a stored part of that question (0 for multiple choice). The tests of §9 pin both halves: a negative-control insert shows the table accepts the pair above, so nobody mistakes the key for the guarantee, and a service test shows a submit never writes such a pair.

Why these columns: stable references (`question_id`, `blueprint_id`) survive a rebuilt database. Answer rows exist only after submit, so per-row points cannot protect an attempt in progress; the start therefore stores everything that later decides its fate: `duration_seconds`, `deadline_at`, `submit_cutoff_at`, `max_points_planned` and `slot_format_json`. Without them a deploy that changes the grace constant, or a re-seed of the blueprint (`src/seed_dzi_blueprint.py:86,135` update blueprint and slot rows in place with `ON CONFLICT ... DO UPDATE`), would change the state or the grading of an attempt in flight; the reviewer's prototype showed the same row at the same instant `lapsed` with a 60 s grace and `grace` with 120 s (Appendix B). No correct answer is stored on an attempt (the review derives it from current content).

### 5.4 Classification, updater, backup

### 6.2 Start and resume

One writer transaction through the lifecycle layer (§7.4), in this order. **Open-attempt handling comes before any blueprint validation**, so a resume never depends on the current blueprint and an open attempt keeps its stored plan and slot format (§4.3).

1. Active account, else `account_unavailable` (read-only outcome).
2. The account's open attempt (no terminal timestamp), if any. Parse its stored plan and slot format; a malformed or inconsistent pair fails closed as C2's `PracticePlanError` does, writing nothing. Then decide from the stored columns and lifecycle `now` only (§7.2):
   - `now < started_at` (the **future-start anomaly**, §7.4; a defense for an **inconsistent row** only: every C3 start calls `admit()`, so, before a recovery lowers the high-water mark and while the clock row is usable (§7.4), `now` cannot be earlier than `started_at`; the branch is reachable after a recovery that did not mark the row, or after a manual change): call `admit()`, mark the row `abandoned_at` (guarded on open) and go on to step 3.
   - `started_at <= now < deadline_at` and the row presents at least one item: **resume**, writing nothing and not admitting.
   - `deadline_at <= now < submit_cutoff_at` (grace): return the same attempt, writing nothing; its page says time is up and offers no start action (§6.3).
   - `now >= submit_cutoff_at`: `admit()`, mark `expired_at` (lazy expiry, §7.2) and go on to step 3.
   - Open but presenting nothing renderable: `admit()`, mark `abandoned_at` (the C2 "stale" rule) and go on to step 3.
3. **Only now, and only to create a new attempt**, read the blueprint (`is_active`, the Part 1 slots) and validate it: exactly the expected contiguous Part 1 slots, kinds only in {multiple choice, short answer}, positive points, `part1_minutes` positive and bounded, no unsupported slot constraint (`topic_id`, `section_id`, `required_asset_type`, `topic_area`). Otherwise `blueprint_unavailable`: no attempt is created (fail closed, not silently ignored); a marking made in step 2 is still committed, because it is true whatever the blueprint says.
4. Build the pools (§4.1). If a kind is short, `pool_insufficient`: no attempt is created; a marking made in step 2 is still committed.
5. Otherwise, after `admit()`, insert: `seed = secrets.token_hex(16)`; sort each pool by id; `random.Random(seed).sample` draws the items of each kind without replacement; items fill the slots of their kind in slot order. From the one `now` of the transaction: `started_at`, `deadline_at = started_at + duration`, `submit_cutoff_at = deadline_at + SUBMIT_GRACE_SECONDS`; `duration_seconds`, `max_points_planned` and `slot_format_json` are snapshotted from the blueprint validated in step 3.

Deterministic: given the stored seed and the same pools the draw and the option order (`quiz_shuffle_options`, `web/services/quiz.py:1242`, seeded by the attempt seed) are reproducible, which is how tests pin them; the stored plan, never a recomputation, is authoritative. The partial unique index makes concurrent starts of one account leave one open attempt; a second `POST` returns it. During grace a start returns the same attempt so that an in-flight auto-submit is never refused by the start that raced it; only at or after the **stored** cutoff does a start expire and replace it.

### 6.3 Attempt page (read-only)

It writes nothing, expiry and clock bookkeeping included. It shows the stored questions in slot order with the **slot number and points** per item (points from `slot_format_json`), options in seeded order **without** correct markers (`quiz_load_questions(..., include_correct=False)`, `web/services/quiz.py:1254`), the visuals the existing loader attaches, and the remaining seconds computed from `deadline_at` and the lifecycle read clock. If the clock is unhealthy the page shows persisted state and says submissions are unavailable (the `submissions_unavailable` pattern, `web/blueprints/quiz.py:257`).

**Three different moments, three different pages (Proposal).** The wording below is a requirement on the Bulgarian copy, not the copy:

| Stored moment | Page |
|---|---|
| Before `deadline_at` | The form and a countdown to the **deadline** only. The grace and the cutoff are never shown. |
| `deadline_at` up to the stored `submit_cutoff_at` (**grace**) | No form. The page says time is up and submission is closing; it offers **no** start action and no countdown. Grace is request latency for an auto-submit already in flight, not working time. |
| At or after the **cutoff** (unmarked or `expired_at` set) | A notice that time ran out and answers cannot be saved, with a **new-start** action: offered only here and on the future-start notice below. A start at that moment expires the old row and creates a new attempt (§6.2). |

An attempt stamped later than lifecycle `now` (an inconsistent row, §7.4) shows a notice that it cannot be continued, with the same new-start action, and no remaining time. The intro page discloses no attempt state (§6.1) and keeps its generic start button; a start pressed during grace returns the grace page itself, which offers no action. (The first draft offered a new start as soon as the deadline passed, although a start during grace returns the same attempt, so for up to the grace length the offered action looped to the same page.)

**Short-answer labels.** The existing loader selects only `id, subquestion_number` for short-answer parts (`web/services/quiz.py:1276`), so a C3 loader must also select `subquestion_text` (a label such as "(1) София"). **Evidence** (reproduced 2026-11-23, Appendix A): across the 132 sub-answers of the 58 readiness-eligible items, **0** labels equal an accepted answer and **1** contains one: question 834, sub-answer 1, whose label is identical to the official prompt, so a student learns nothing the prompt does not already show. Label shapes also matter: of the 126 labels in the 56-item pool, 19 equal the prompt and 23 sit inside it (121 labels in the final 53: 17 and 23), so showing every label would repeat question text. **Rendering rule (Proposal): do not show a label that equals, or is contained in, the prompt** (compared after the existing normalizer, `quiz_normalize_text_answer`, `web/services/quiz.py:369`); show the rest. In the final 53-item pool that shows 81 of 121 labels and hides 40, and no shown label contains an accepted answer that the prompt does not already contain. A test keeps that true for the active pool (§9).

### 6.4 Submit and bounded input

Fields: `q_<question id>` carrying the stored option key (never a display letter) and `a_<question id>_<n>` carrying text for sub-answer `n`; both are matched by a fixed pattern and only for ids in the stored plan, and an `a_<id>_<n>` field is accepted **only when `n` is a stored part number of that planned question**. Everything else is ignored: the matcher `grade_quiz_text_answers` (`web/services/quiz.py:659`) turns any submitted part number into a graded row, so on the prototype a submitted part 9 of a one-part item became an extra row (Appendix B; reproduced 2026-11-23). A field sent twice counts as unanswered (as `web/blueprints/practice.py:99`).

**Proposed bounds** (pending review; enforced by the service, never by a table `CHECK`):

- **Body.** The application-wide limit is about 100 MiB (`web/app.py:175`, `src/practical_uploads.py:24-29`) and the existing open-answer field has no length limit (`web/templates/quiz_attempt.html:160-168`), so the route sets a 64 KiB limit of its own. **Overflow fails closed (Proposal):** a request without a usable `Content-Length` is refused with 411 **before the form is read**, and a declared length over 64 KiB is refused with 413 before the form is read. **A declared length must also be true (Proposal).** After the 411 and 413 checks the service sets the request's `max_content_length` to 64 KiB, reads the body once into Werkzeug's cache (`get_data(cache=True)`, so the later form parse reads the same bytes) and requires the **byte count to equal `request.content_length`**. That is the value Werkzeug derives from the header, not the raw header string, and it is `None` for a chunked request, which is why chunked bodies end at the 411 branch and are never compared. A **malformed** `Content-Length` (non-numeric or negative) is `0` in Werkzeug 3.1.9, not `None` (reviewer's log, Appendix B, revision-4 review): it passes the 411 branch and fails closed, as 400 when a body is delivered (the byte count differs from 0) and as the `empty` outcome of step 7, with nothing stored, when none is; Gunicorn 23.0.0 refuses a malformed header before the application sees it. A mismatch, short, or long under a declared length below 64 KiB, answers **400 before any field is parsed, graded or stored**, writes nothing (the clock row included) and keeps the client's draft. The order is fixed: 411, 413, bounded read and length equality, then form parsing, then every rule below. A valid `Content-Length` does not guarantee delivery: the reviewer, through the real Gunicorn 23.0.0 parser and Werkzeug 3.1.9, sent `Content-Length: 1000` with 500 bytes delivered and got 200 with the value cut to 498 characters instead of 998, which the one-shot submit would have stored (Appendix B, revision-3 review). The author's scratch model of the rule (Flask 3.1.3, Werkzeug 3.1.9, WSGI with `wsgi.input_terminated` true, no Gunicorn; Appendix A) gives, for the four cases the design must separate: **complete** declared body, accepted (200); **chunked** or missing length, 411; **oversize** declared length, 413; **short** declared body (1000 declared, 500 delivered), 400, where the revision-2 rule answered 200 with a 494-character value. A stream that delivers more than it declared, under a declared length **below 64 KiB**, is read only up to the 64 KiB limit (65,536 bytes read from a 1,000,000-byte stream under a declared 500) and refused 400. **At a declared length of exactly 65,536 that sentence does not hold**: the read stops at the limit, which equals the declared length, so the excess is not seen and the answer is 200; the parsed bytes are exactly the declared bytes and nothing beyond them reaches grading (reviewer's log: a 70,000-byte stream under a declared 65,536; Gunicorn cannot over-deliver, so this case is a WSGI-level one). The alternative of reading at most the limit plus one byte and refusing on overflow would need a hand-written form parser and is not proposed. The reason is measured: with a per-request `max_content_length` of 65,536, Werkzeug 3.1.9 refuses a declared oversize body with 413, but a terminated chunked body of 70,000 bytes answers 200 with the value **silently cut to 65,534** (reviewer-found; author-reproduced 2026-11-23, Appendix A). A cut value would be graded and stored, contradicting "nothing written". The tracked proxy configuration buffers requests (`deploy/nginx/learnpilot.conf:86`, `proxy_request_buffering on`), but that is configuration, not something the service may rely on, and the deployed proxy was not inspected.
- **Text.** At most 200 characters per answer (Python code points), `maxlength` in the markup, no NUL, at most one value per field; a value over the bound or containing NUL refuses the whole submit with 400 and nothing is written. **Evidence**: the longest individual accepted answer in the final 53-item open pool is **66** characters (question 140; author-reproduced 2026-11-23 on the disposable build, over the reviewer's final id list; revision 2 cited 73, which belongs to question 202, now excluded by the stimulus layer of §4.1); a full attempt has at most 45 answer fields (15 multiple choice and 30 short-answer parts, the ten largest items having three parts each). A browser that honours `maxlength` cannot exceed **54,509 bytes** (45 fields, 200 UTF-16 units of a three-byte character each in the 30 text fields, four-digit ids; author-reproduced model, 2026-11-23), which is under the 65,536 limit. A hand-crafted body of 200 four-byte characters per text field reaches 72,509 bytes, over the limit, and is refused. No honest submission is refused by the limit.
- Nothing from the client names a role, owner, plan, seed, score, timestamp or deadline.

Single transaction, idempotent, mirroring `quiz_submit_attempt` (`web/services/quiz.py:2298-2401`) and `submit_practice` (`web/services/practice.py:771-817`). A path that writes calls `admit()` first; a path that does not write ends with `discard()` and does not admit (§7.4).

1. Account, then the attempt by `(id, user_id)`; none, `not_found`. Read-only outcome.
2. `submitted_at` set: `already_submitted`, **no write of any kind** (the lifecycle `discard()`), so a retry leaves every table, the clock row included, unchanged.
3. `abandoned_at` set: `abandoned`, refused, nothing written (an old tab can never grade a replaced attempt). `expired_at` set: `expired`, nothing written.
4. Unmarked, `now < started_at` (future-start anomaly, §7.4): refused, **nothing graded and nothing written**; the row is left as it is and the next start marks it `abandoned_at`.
5. Unmarked and `now >= submit_cutoff_at` (the **stored** cutoff): `expired`; `admit()`, mark `expired_at` (guarded on open) and commit; no answer rows. Otherwise continue (before the deadline, or in grace).
6. Parse the plan and the slot format; they must agree (25 and 25, kinds and points as the start stored them), else fail closed with nothing written. The **kind and slot points of every item come from `slot_format_json`, never from the current blueprint**: a re-seed after start changes neither the grading nor the maximum of this attempt. Presentable items = stored ids that still satisfy the per-item predicate (the item still renders or grades as its stored kind; for short answer, its current part weights still sum to the slot's stored points). This is not a rebuild of whole pools, so a later addition to the stimulus list (§4.1) does not drop an item the student already saw. None presentable: `stale`, nothing written.
7. No usable answer: `empty`, nothing stored, the attempt stays open (§6.7). Read-only outcome.
8. `admit()`; grade (§6.5), insert one row per presentable multiple-choice slot and per short-answer part (each row: `question_id` equal to the plan entry for its slot; `kind` from the slot format; `points_possible` the slot's points for a multiple-choice row and the stored part weight for a short-answer row, never the slot's points once per part, which would give ten three-part items 15 + 90 = 105 instead of 45; the part weights of a slot sum to its stored points, §6.5), then `UPDATE ... WHERE open` with `submitted_at = now` and verify the row count. Any inconsistency raises and rolls back; nothing partial persists.

### 6.5 Grading and scoring

- **Multiple choice.** Chosen key must equal a current stored option key; verdict against the one correct key (`quiz_correct_mc_letters_by_id`, `web/services/quiz.py:1322`; C2 `_grade`, `web/services/practice.py:735`). The slot's points from `slot_format_json` (1 today).
- **Short answer.** Reuse the pure matcher `grade_quiz_text_answers` (`web/services/quiz.py:659`) with accepted answers from `correct_answer` and `answer_alternatives` (`:397`) and the existing ordered or order-independent mode (`:406`; 54 ordered and 4 order-independent among the 58 readiness-eligible items). Limits to state to students, not to hide: exact match after NFKC, whitespace collapse, quote folding and `casefold` (`:369`); no typo, synonym, number-format, unit or word-order tolerance; no partial credit inside one sub-answer; the grader cannot judge meaning. A correct answer phrased differently scores zero.
- **Weights.** The existing grader awards 1 point per sub-answer (`:638-656`), which would cap a three-point, one-part item at 1. C3 instead awards the stored `fill_in_subquestions.points` of each correct part. **Evidence**: 56 of 58 ready items sum to 3 (34 as 1+1+1, 20 as a single part of 3, 2 as 1+2); the other two are 1+1 and 1+1+1+1. The 4 order-independent items all have equal weights, which makes matching weights to parts unambiguous. The weight rule of §4.1 (sum must equal the slot's points; order-independent items need equal weights) keeps awards whole and slot-true; the two non-conforming items stay out until reviewed. These shapes are counted over the 58 readiness-eligible items, before the stimulus layer; the three items that layer removes (§4.2) are one 1+1+1 item and two single-part items of 3. **In the final 53-item pool** the weights sum to 3 for every item: 33 as 1+1+1, 18 as a single part of 3, 2 as 1+2 (121 parts; author-reproduced 2026-11-23, Appendix A). Each short-answer row therefore carries a part weight (1, 2 or 3) as `points_possible`, never the slot's 3 once per part (§5.3, §6.4 step 8).
- **Persisted verdicts.** Each row stores verdict, possible and awarded points and `grader_version`; the score is the sum of awarded points of presentable rows and the maximum the sum of possible points. Neither is recomputed later.
- This is **mixed effective scoring**: unlike assignment attempts, where open answers are shown as an informational subtotal beside the stored multiple-choice score (`web/services/quiz.py:876-912`), the simulation score includes auto-graded short answers.

### 6.6 Result, saved score and the current-content caveat

Only a submitted attempt has a result; others give the generic 404. It shows `score_points / score_max` from the stored row, the multiple-choice and short-answer subtotals from the stored answer rows, and a review per slot. Same rule as C2 (`docs/STUDENT_PRACTICE_DESIGN.md` §4): stored ids, verdicts and points are never recomputed; prompts, options, correct answers, accepted answers and explanations are read from **current** content, so after a content change a review can disagree with the saved verdict; items no longer presentable are omitted and counted, and an empty review still returns the saved score. Correct answers appear only here, after submission, never in an attempt page or answer row. Reuse: the multiple-choice review partial (`web/templates/_multiple_choice_result_review.html`, which numbers by `loop.index` and needs a slot-number parameter, so a render-equality test pins the old result page) and the explanation fetchers; the short-answer review is a new block (the assignment page's block carries teacher-override state, `web/services/quiz.py:1971-2012`). The page must state that the short-answer check is automatic and strict, and that the 90 minutes are the simulation's limit.

### 6.7 Incomplete, timed-out, maximum, later eligibility

- **Maximum.** Part 1 only: `max_points_planned` is the sum of the snapshot points (45 for a full plan); `score_max` is the sum over presentable rows, so it equals 45 unless an item became unpresentable. Never the blueprint's 100.
- **Incomplete.** Unanswered items score 0 and are stored; a submission needs at least one usable answer, meaning a stored option key of a plan question or a non-blank text for a plan sub-answer of a stored part (an all-empty submit is refused, writes nothing and stays open).
- **Timed out.** An attempt not submitted before its stored cutoff is `expired`: no answers are stored, no score, no result, no count. The page says time ran out. **Open**: a late submit is lost; the alternatives (accept it unofficially, or save drafts on the server) are listed in §11. The only mitigation proposed is the browser-local draft and the elapsed-time countdown of §6.8, which lowers the chance of a late auto-submit but cannot rescue one the server refuses.
- **Later C4 (separate scope).** Stored data lets C4 take only attempts with `submitted_at` set and `score_max = max_points_planned` as a labelled "DZI Part 1 simulation" source, with `grader_version` and the short-answer caveat, never merged into C2 or assignment progress. Nothing here defines that screen or any rollup.

### 6.8 Client countdown, local draft and submit (Proposal; deferred to C3.5)

Nothing here is written by this PR or by C3.1-C3.4; the late-submit rule of §6.7 needs it defined now. The server decides every outcome (§7.3); the client only reduces the chance of a late submit and of lost work. The two existing scripts are a **model only** and cannot be reused unchanged:

- The assignment countdown (`web/templates/quiz_attempt.html:209-267`) decrements a counter once per fired `setTimeout` (`:264-265`), so a callback delayed by a suspended device is counted as one second. Run against a virtual clock, a 10-minute suspend submits it at 1,199 s of a 600 s deadline with a 660 s cutoff, where the server refuses it and every answer is lost (reviewer's model, Appendix B).
- The draft script (`web/static/js/quiz-draft-autosave.js`) keys its storage `learnpilot:quiz-draft:<attemptId>` (`:20`), which would collide with an assignment attempt of the same number; it recognises only `q_` and `open_q_` names (`:33`, `:99`), so it ignores `a_<id>_<n>`; and although its comment says it clears on the result page (`:138-141`), no tracked template or script calls its `clear` (searched `web/` and `tests/`).

The C3 behaviour, a new client file and template block with their own names:

1. **Countdown from elapsed real time.** The attempt page carries the server's remaining seconds to the **deadline** (computed at render from `deadline_at` and the lifecycle read clock). The client records the load instant on both the wall clock and the monotonic clock and shows `server remaining - elapsed`, taking the larger of the two elapsed readings, so that neither a suspend the monotonic clock may not count (browser behaviour across a suspend was not measured here; the manual acceptance records it per browser) nor a wall clock stepped backwards can give back time. Timer callbacks only refresh the display; none is counted. It recomputes on every tick, on `visibilitychange` to visible and on `pageshow`. The display is advisory: the server owns the deadline. Trade-off for review: a student who steps the device's wall clock forward ends the countdown early and submits early; that is accepted, because the alternative (trusting the monotonic clock alone) can lose every answer after a suspend.
2. **Submit once at or past zero.** At or past zero the client submits the form **once** (a flag), by the same request as a manual submit. It sends no reason, time or flag, because the server accepts nothing a client claims (§6.4). If the page wakes already past the cutoff it still submits once, because only the server's clock decides, but it **does not claim the answers were saved**: it shows only a neutral "submitting" message and leaves every statement of success to the server's result page. This is a convenience of an open page, **not a background close**: a closed tab or a suspended device submits nothing, and the row then simply lapses and is expired lazily (§7.2).
3. **Local draft, C3-specific.** Storage key `learnpilot:dzi-part1-draft:<scope>`, where the server renders `<scope>` as `<attempt id>:<owner user id>:<started_at>` on the attempt page. The draft covers the C3 field names only: radios named `q_<id>` and text inputs named `a_<id>_<n>`, restored only into a control with the same name (and, for a radio, the same option key). The stored payload repeats the scope; a draft whose scope differs from the page's is **never restored** and is deleted, so a draft cannot be reused across owners, nor across a restored database that reissues an attempt number. Saves are best-effort and silent on a storage error.
4. **The draft survives a refused submit and is cleared only on a terminal page.** It is not cleared by submit, so a refused (400, 411, 413), empty or redirected submit loses nothing. It is cleared when the **result page** of that attempt loads and when the **expired or abandoned notice** of that attempt loads (both render a clearing call with the same scope). It is not cleared by a sign-out, which the client does not see; on a shared device an unfinished draft stays in the browser profile until one of the two pages loads or browser data is cleared, a limitation the approved copy must state.
5. **Without JavaScript** there is no countdown, no auto-submit and no draft: the student must submit manually before the deadline, and the page says so (the server still decides).

Tests and acceptance (no JavaScript test runner exists, and none is added: `AGENTS.md` allows no npm). Server-rendered markup tests assert the data attributes, the scope string, the field names and that a terminal page carries the clearing call, in the style of `tests/test_quiz_attempt_render.py:2174-2182`. Manual browser acceptance, recorded in the C3.5 PR, covers each case: a normal countdown to zero and one auto-submit; a laptop suspended across the deadline and across the cutoff; a hidden tab across the deadline; a refused and a redirected submit keeping the draft; the draft cleared on the result and on the expired notice; a draft of another attempt or owner not restored; JavaScript disabled.

## 7. Time

### 7.1 App timing is a proposal

Official timing is not established by tracked evidence (§3.2). **Proposal**: `duration_seconds = blueprint.part1_minutes x 60` at start (5400 today) and a submit grace `SUBMIT_GRACE_SECONDS = 60`, both app timing, both pending review. The duration is stored per attempt as `duration_seconds`; the grace is stored as the **cutoff** `submit_cutoff_at = deadline_at + SUBMIT_GRACE_SECONDS`, computed once at start (§5.3). The constants are read only when a new attempt is created, so **changing either affects only attempts started afterwards**. The grace only absorbs request latency of an auto-submit at zero; it is not extra working time and is not shown as such (§6.3). The existing assignment grace is 15 minutes for a different purpose (`web/services/lifecycle.py:50`). These are timing proposals: approving them is not an activation (§8) and says nothing about the official exam.

### 7.2 States and lazy expiry

State is a pure function of the stored row and lifecycle `now`, reading only stored columns (never the constants):

| State | Stored condition |
|---|---|
| **submitted** | `submitted_at` set |
| **abandoned** | `abandoned_at` set |
| **expired** | `expired_at` set |
| **future-start** (anomaly of an inconsistent row, §7.4; holds only while `now` is earlier than the stamp, and before a recovery, while the clock row is usable, `now` cannot be earlier than a consistent row's `started_at`) | no terminal timestamp and `now < started_at` |
| **open** | no terminal timestamp and `started_at <= now < deadline_at` |
| **grace** | no terminal timestamp and `deadline_at <= now < submit_cutoff_at` |
| **lapsed** | no terminal timestamp and `now >= submit_cutoff_at` |

Every upper bound is exclusive: a submit at the exact `deadline_at` is in grace, and a submit at the exact `submit_cutoff_at` is refused, as the lifecycle cutoff is exclusive (`web/services/quiz.py:2318`). Test: the same stored row at the same `now` has the same state whatever `SUBMIT_GRACE_SECONDS` is (the prototype showed the first draft's derived cutoff give `lapsed` at 60 s and `grace` at 120 s; Appendix B).

**There is no background close.** No job, timer thread, cron or startup hook exists or is proposed. "Lapsed" is an interpretation every reader applies; the row gets `expired_at` only inside a write transaction of the owner's own `POST` (start or submit), and then `expired_at = now >= submit_cutoff_at`, which is what the row-local `CHECK` of §5.3 states. Consequences, each a future acceptance test (§9): an untouched lapsed row stays "open" in storage and still occupies the account's single open slot until that account's next start or submit; no read changes it; any aggregate must test stored `submitted_at`, never derived state; a periodic cleanup, if wanted, is a separate scope with its own approval. The terminal timestamps are coherent by construction: `submitted_at` lies in `[started_at, submit_cutoff_at)`, `expired_at` is at or after the cutoff, and `abandoned_at` carries no ordering against `started_at` because the future-start anomaly (a start, for an inconsistent row) and the recovery rule (`clock-recover`, §7.4) stamp it at a time that can be earlier than that.

### 7.3 Races, refresh, old tabs

| Situation | Result |
|---|---|
| Submit before the deadline | Graded and stored |
| Submit at or after the deadline, before the stored cutoff | Graded and stored (grace) |
| Submit at or after the stored cutoff | `expired`, nothing graded; row marked once; retry writes nothing |
| Double submit, or two tabs | One answer set; the second finds `submitted` and writes nothing |
| Submit racing a start of the same account | The writer lock orders them; a start cannot abandon an unexpired, presentable attempt, so a submit never loses to it; a lapsed attempt is expired first and the late submit is refused |
| Old tab after a new attempt | Its id differs; it can only reach its own row, which is submitted, expired or abandoned: no write, no effect on the new attempt |
| Refresh | Same stored plan, slot format, seed, order and `deadline_at`; the remaining seconds are recomputed, never reset; nothing written |
| Client clock wrong or JS off | The countdown is display only; the server decides from its own clock; without JS the user submits manually (§6.8) |
| Device suspended, or tab hidden, across the deadline | On wake the client recomputes from elapsed real time and submits once at or past zero (§6.8). Accepted if the stored cutoff has not passed; otherwise refused as `expired` and the answers are lost, as for any late submit. The client never claims "saved" |
| Session lost during the attempt (expired, signed out elsewhere) | The submit `POST` is answered by a redirect to `/login?next=<path>` (`web/app.py:529`, `docs/AUTH_ROUTE_CONTRACT.md:55-57`) and the form body is dropped; nothing is written. The answers survive only in the browser-local draft (§6.8). The deadline does not pause. Session lifetime is absolute: 30 days for student and teacher, 12 hours for admin (`web/services/accounts.py:29-33`), so loss mid-attempt needs expiry at that moment or a sign-out. After signing in, the attempt page restores the draft if time remains, and clears it on the expired notice |
| Row stamped ahead by a forward clock fault, the clock then corrected, **before any recovery** | On the same boot, with a fault over the 60 s step tolerance, every writing request is 503 (`clock_regression` while the wall clock is more than 5 s behind the mark, `clock_step` after that; the clock then `suspect`), and no answer row is stored. A fault of at most 60 s can be admitted once the wall clock is within 5 s of the mark, and such a row keeps up to 60 s. The read state is **not** `future-start`: every C3 start called `admit()`, so `high_water_at >= started_at` and, while the clock row is usable, lifecycle `now = max(wall, high_water_at)` is never earlier than `started_at` (reviewer's prototype, wall clock 0 s to 6 h behind the stamp, Appendix B, revision-4 review). The 503 refusal is the protection here, and, once a fault is recorded, it ends only with an operator's `clock-recover`; for a reboot before any fault is recorded, see the next row (§7.4) |
| Stored row stamped later than lifecycle `now` (an **inconsistent row**: after a recovery that did not mark it, such as one run by a build without the marking, or after a manual change) | Submit refused with nothing graded and nothing written, only while `now` is earlier than the stamp; the next start marks it `abandoned_at`. A defense for an inconsistent row, not prevention: it ends when `now` reaches the stamp, and a stamp already earlier than the verified time never looked future (§7.4) |
| Forward fault present from a boot's first lifecycle write, corrected with no lifecycle transaction before the next reboot, then no transaction until the wall clock is within the 5 s regression tolerance of the high-water mark | **Not detected, with or without the recovery proposal** (§7.4, reviewer's prototype): no fault recorded, clock `ok`, no recovery is prompted or run, and every attempt started during the fault keeps its extra time. A transaction that comes while the wall clock is still further behind the mark is refused `clock_regression` and records a fault. A known limitation, not a guarantee |
| Operator runs `clock-recover` while a C3 row is open (any stamp, any age) | **Proposal (C3.2):** the row is marked `abandoned_at` at the verified time in the recovery transaction; a later submit is refused as `abandoned` with no answer rows, however much real time has passed; the next start creates a new attempt if the blueprint and pools pass. An honest open attempt is abandoned too (§7.4) |
| Complete body: declared length present, at most 64 KiB, bytes delivered equal it | Accepted for parsing; every later rule applies (§6.4) |
| Chunked body, or no usable `Content-Length` (`request.content_length` is `None`) | Refused 411 before the body is read or any form field is parsed; nothing graded, nothing written; the draft is kept (§6.4, §6.8) |
| Declared length over 64 KiB | Refused 413 before the body is read; nothing graded, nothing written; the draft is kept |
| Short declared body (fewer bytes delivered than declared, for instance 500 of 1000), or more than declared under a declared length below 64 KiB | Refused 400 after the bounded read and before any field is parsed, graded or stored; the clock row and every table unchanged; the draft is kept (§6.4) |
| Declared length of exactly 65,536 with a stream that delivers more | The read stops at the declared length, so the excess is not seen: 200, and only the declared bytes are parsed (§6.4). Not a refusal, and not a way to store more than was declared |
| Malformed `Content-Length` (`request.content_length` is `0`, not `None`) | With a body delivered, 400 before any field is parsed; with none, the `empty` outcome, nothing stored. Gunicorn refuses the header before the application (§6.4) |
| Constant `SUBMIT_GRACE_SECONDS` changed in a deploy | Rows already stored keep their stored cutoff and state; only new attempts use the new value |
| Request body from a client claiming a time | Ignored |

### 7.4 Clock failure

**Proposal**: take time from `web/services/lifecycle.py` as the quiz does, with an explicit contract for what C3 calls and what it does not.

**What the layer gives.** Every C3 `POST` runs in `write_transaction` (`web/services/lifecycle.py:1099`), which takes the writer lock and refuses a regressed, stepped, unsynchronised or suspect clock with `LifecycleUnavailable` before the first statement; the refusal is answered as 503 (`web/app.py:578`). A clock fault stores only the clock row's own fault record (`_record_clock_fault`, `:909`) and no C3 row. Reads use `read_clock` and `read_snapshot` (`:875`, `:887`) and write nothing. C2 uses the raw UTC clock because it is untimed (`web/services/practice.py:525`); a binding deadline is the reason C3 should not.

**1. Admit on every writing path, and only there.** `write_transaction` alone does not raise the high-water mark or write the boot anchor: that is `admit()` (`:975`), and the layer's own contract is that nothing is written before it (`:935-941`). Without it the prototype accepted a clock moved back one hour and showed 9,000 s remaining on a 5,400 s attempt; with it the same step was refused as `clock_regression` (reviewer-found, Appendix B). So:

| Path | `admit()` | Ends |
|---|---|---|
| Start creates an attempt | before the insert | commit |
| Start marks `expired_at` or `abandoned_at` (§6.2 step 2) | before the marking | commit, even if the start then returns `blueprint_unavailable` or `pool_insufficient` |
| Submit stores answers | before the first answer row | commit |
| Submit marks `expired_at` (§6.4 step 5) | before the marking | commit |
| Read-only outcomes: start resumes, `account_unavailable`, grace return, or refuses with nothing marked; submit `not_found`, `already_submitted`, `abandoned`, `expired` already marked, future-start refusal, `empty`, `stale`, a malformed plan | **never** | `discard()`: nothing is written, the high-water mark included |
| `GET` of the intro, an attempt or a result | never: no writer transaction. The attempt and result pages read inside a read snapshot (a read transaction only, §6.3); the intro needs none | nothing written; the snapshot is released |

A read-only outcome still runs the clock check at the start of its transaction, so an unusable clock answers 503 even for a retry that would have written nothing.

**2. No `check_factual` on C3 rows.** `check_factual` (`:962`) records a clock fault and raises when any factual timestamp is later than `now`. Applied to a C3 row it would put the one shared lifecycle clock into `suspect` and block every assignment write because of a single student's row (prototype, reviewer-found, Appendix B). C3 never calls it, on any of its own columns.

**3. Before a recovery the 503 clock refusal protects a forward-stamped row; recovery abandons open C3 rows; one case remains even then (Proposal).**

*What the existing tools do (Fact).* `clock-recover` (`src/manage_lifecycle.py:515`) and `clock-inspect` (`:492`) read `quiz_assignments` and `quiz_attempts` (`_factual_values`, `:346-358`; `clock_lists`, `:363-402`); they **neither list nor hold C3 rows**, and recovery sets the high-water mark to the verified time, which can be earlier than a row stamped during a forward clock fault. An assignment in the same position is held with `clock_review`, and `hold-resolve` keeps the hold until lifecycle time has passed every stamp (`:607-616`). A C3 row has no equivalent.

*Before a recovery: what protects the row, and what the `now < started_at` guard can see.* Every C3 start calls `admit()`, so the same commit sets `high_water_at` to `started_at` (`web/services/lifecycle.py:975-990`), and both clock paths use `now = max(wall, high_water_at)` (`:882`, `:1060`). **Before a recovery lowers the high-water mark, and while the clock row is usable, lifecycle `now` cannot be earlier than a C3 row's `started_at`.** On a corrected clock the wall clock is behind the mark. On the same boot, with a fault over the 60 s step tolerance, every writing request is therefore refused 503 (`clock_regression` while the wall clock is more than 5 s behind the mark, `:1056-1059`; `clock_step` after that, `:1070-1072`) and the clock goes `suspect` until an operator recovers it. A fault of at most 60 s can be admitted once the wall clock is within 5 s of the mark, and such a row keeps up to 60 s. Reads show `max(wall, high_water_at)`, so, while the clock row is usable, the state is never `future-start`. The reviewer's prototype showed the mark, `now` and the read state this way with the wall clock 0 s to 6 h behind the stamp, and the 503 where the wall clock was more than 5 s behind the mark (Appendix B, revision-4 and revision-5 reviews, `future_start_before_recovery`, `same_boot_correction_by_fault_size`; the reviewer's, not re-run by the author). With a missing or unreadable clock row, `read_clock` returns the raw wall clock with `healthy` false (`web/services/lifecycle.py:877-880`), so a read can derive `future-start` for a forward-stamped row; every write is still refused 503 `clock_row_invalid` (reviewer's prototype, `unusable_clock_row_before_any_recovery`). The earlier text of this document called the `now < started_at` guard a defense "for the time before recovery"; that was wrong, because the guard cannot fire then, and it is withdrawn.

*What the `now < started_at` guard is for.* The rule (§6.2, §6.4, §7.2) makes a row with `started_at > now` **future-start**: the page shows persisted state and a notice that it cannot be continued, a submit is refused with nothing graded and nothing written, and the next start marks it `abandoned_at` (that marking is a writing path, so it calls `admit()`; it never calls `check_factual`, so it never marks the shared clock `suspect`). It is kept as a defense for an **inconsistent row**; as a **write**-path guard it is reachable only after a recovery that did not mark the row (a tool without the C3 change, or one of the rejected alternatives below) or after a manual change, while a read can also derive the state from an unusable clock row (above). It is a **separate** protection from the 503 refusal and it cannot be durable: state is computed from the stored row and `now` (§7.2), so **once `now` reaches a false `started_at` the row cannot be told apart from a healthy one**, and **a stamp already earlier than the verified time never looks future at all**. The reviewer's reproduction with the real `clock-recover` (Appendix B, revision-3 review, S5): after a 6 h forward fault recovered 10 minutes in, the row was refused at first; when the student sent no `POST` until real time reached the stamp, the row was `open` with 5,399 s shown and a submit saved 45/45 at 21,601 s after the true start. After a 1 h forward fault recovered 2 h in, the row was never future-stamped and a submit saved at 7,201 s of true elapsed time against a 5,400 s limit. Earlier text of this document said such a row "neither gains working time" and that the design needed no `manage_lifecycle` change; both statements were wrong and are withdrawn.

*Proposal for C3.2 (recovery, decision for the owner, §11 row 13).* Inside its existing transaction, `clock-recover` sets `abandoned_at` to the **verified time** on **every open C3 row**, meaning a row with none of `submitted_at`, `expired_at`, `abandoned_at` set, with the statement guarded on that condition so a terminal row is never touched. `clock-inspect` reports, read-only, **only the count** of the rows that would be marked. The recovery's existing audit line adds the same count. Everything else `clock-recover` does stays as it is: the holds and retention floors for assignments, the new high-water mark, the confirmed clock state, the refusal when the local clock disagrees with the verified time. The marking does not depend on `--suspect-from` or `--suspect-to`. A recovery that finds no open C3 row writes no C3 row. The change lands **with or before the first C3 writer** (C3.2, whose start is that writer), never later and not in storage-only C3.1, where no row can exist. After recovery the abandoned row follows the existing rules: a submit is refused as `abandoned` with no answer rows however much real time has passed, the owner's page shows the abandoned notice, and the next start creates a new attempt if the blueprint validates and both pools pass.

*Tooling contract for schemas (Fact, verified at this base).* Every `manage_lifecycle` command, `clock-inspect` and `clock-recover` included, opens the database and calls `require_matching_schema` before any command runs (`main`, `src/manage_lifecycle.py:1481-1482`). It refuses the command, exit status 2 and nothing written, when migrations are **pending** (`schema_problems`, `:124-137`) and also when the database holds applied migrations the build does not ship. For this proposal that means: (a) a build whose tool names `dzi_part1_attempts` runs only against a database that has 027 applied, so the C3 statements need no "table missing" branch and must not run before that check; (b) a database with 027 applied cannot be recovered by an older, pre-027 tool build, so rolling the code back (§5.5) is not a way around this; **but a C3.1 build ships 027 without the marking (C3.1 is storage only, §10), so it passes `require_matching_schema` and its `clock-recover` leaves open C3 rows open** (reviewer's prototype, `S5b[current]`: exit 0, row still open, 45/45 saved at 21,601 s; Appendix B, revision-4 review). The sequencing of §10 is unchanged and right for the forward order; the added rule is that **once a C3 row may exist, a recovery must not be run by a build without the marking**; (c) the change adds no migration and no new refusal. `clock-recover` is also a step of the restore sequence (`docs/DEPLOYMENT.md:1968`); after a restore it would abandon any C3 row that was open in the restored copy, which agrees with §5.4 (a restore drops later attempts).

*Cost (Proposal, stated, not hidden).* An **honest** attempt that is open during a recovery is abandoned too: its student sees the abandoned notice, the answers typed so far are lost (the browser draft is cleared by that notice, §6.8 item 4) and a new attempt means a new draw and full time. Marking every open row is proposed because a narrower rule depends on the operator declaring the right suspect interval, and it misses the 1 h case (S5c) when no interval is declared. The cost is bounded by how rarely a clock incident needs recovery.

*Remaining limitation, with the proposed rule too (reviewer's prototype).* The rule acts only when `clock-recover` runs. A forward-stamped row may never prompt one. The conditions are: the first lifecycle write of a boot anchors that boot on a clock that is ahead and reports synchronised; later transactions of that boot agree with the anchor and pass the step check while the clock stays ahead, so **every attempt started on that boot before the correction is forward-stamped, not only the first**; the clock is corrected with **no lifecycle transaction between the correction and the next reboot**; and after the reboot the clock reports synchronised and **the next transaction comes when the wall clock is no more than the 5 s regression tolerance behind the high-water mark**. A transaction on the same boot between the correction and the reboot is refused 503 and records a fault (`clock_regression` while the wall clock is more than 5 s behind the mark, otherwise, over the 60 s tolerance, `clock_step`). A first transaction after the reboot while the wall clock is still further than 5 s behind the mark is refused as `clock_regression`. Either records a fault and prompts a recovery. When the conditions hold, no fault is recorded and the row looks healthy: a new boot has no monotonic comparison (`web/services/lifecycle.py:1073-1083`) and there is no regression (`:1056-1060`). In the reproduction a row stamped 1 h ahead saved 45/45 at 8,400 s of true elapsed time against a 5,400 s limit, with the clock `ok` and no recovery run (`forward_stamp_then_corrected_then_reboot`). In a second reproduction, attempts started 0, 600 and 1,200 s into one 1 h fault all saved, at 8,400, 7,800 and 7,200 s of true elapsed time (`several_writes_during_fault_then_corrected_then_reboot`). With the same fault, a correction and reboot at +10 min and the next write at +11 min was refused `clock_regression` with the clock `suspect` (`corrected_reboot_next_write_before_mark`). On a host with no boot identity there is no step check, so the same correction needs no reboot (`no_boot_identity_no_reboot`); production is expected to have one, and the deployed host was not inspected. In the first reproduction, without the reboot, the same correction is refused as `clock_step` and the clock goes `suspect` (`control_same_boot`); the reviewer's reproduction of a transaction between the correction and the reboot was refused `clock_step` once the wall clock was past the mark, and a transaction after the reboot `clock_suspect` (`transaction_between_correction_and_reboot`). **This design does not prevent that case, with or without the proposal, and proposes nothing for it.** It is an accepted limitation for the owner to confirm before activation, together with the decision of §11 row 13. The reviewer's prototype, not C3 code, produced these figures; the author did not re-run them, and how often a production host could report a wrong clock as synchronised was not measured. Such rows would also be C4-eligible (§6.7).

*If the owner prefers a narrower rule or no `manage_lifecycle` change.* The limitation above remains in every case. The case below must then be recorded as a **further accepted limitation**, not as prevention: a row stamped during a forward clock fault, once real time has reached its false stamp or when the stamp was already earlier than the verified time, is indistinguishable from a healthy row; it can carry up to the fault's offset of extra working time (6 h in S5b, 1 h in S5c) and be scored, and would be C4-eligible (§6.7). With the narrower rule that abandons only rows in a declared interval or later than the verified time, S5b is caught and S5c is caught only when the operator declared an interval that contains its stamp.

Trade-offs, for review: (a) a clock fault blocks C3 writes together with assignment writes until an operator recovers the clock (`docs/DEPLOYMENT.md` clock commands); (b) the outage does not pause the deadline, so a student refused during a fault may find the attempt expired afterwards; (c) every C3 attempt that is open when an operator runs `clock-recover` is abandoned, honest or not (the cost above), which is preferred to a forward-stamped row regaining working time; (d) tests use the existing `lifecycle_time` helper (`tests/support.py:140`), not hand-patched clocks, and the recovery tests drive the real `clock-recover` through the CLI entry as `tests/test_lifecycle_operator.py:50-51` does.

- **Start and resume.** One open attempt per account under concurrent starts; resume writes nothing. **Order:** with the blueprint tampered, an open attempt still resumes and a start with none open returns `blueprint_unavailable`; after the blueprint is re-seeded with other points, the open attempt still shows its stored kinds and points. **Grace page:** during grace, a start returns the same attempt and the page offers no start action; at exactly the stored cutoff the page offers one and a start expires the old row and creates a new attempt in one transaction. Stale row abandoned; malformed plan or slot format fails closed; a future-stamped row is abandoned by the next start (which calls `admit()`) and a normal new attempt is created only if the blueprint and pools pass, else the marking alone is committed.
- **Submit.** Idempotent (second submit changes no row and not the clock row); bounds: over-length, NUL, duplicate fields, unknown ids ignored, an `a_<id>_<n>` with `n` not a stored part ignored (no extra graded row); **a missing `Content-Length` and a declared oversize body are refused before the form is read, and a terminated chunked body over the limit is refused with nothing graded, so no truncated value reaches the matcher**. **Declared length, driven as WSGI with `wsgi.input_terminated` true (as the reviewer's check was):** a complete body with its declared length is accepted; a chunked body (`request.content_length` is `None`), small or over the limit, is 411; a declared length over 64 KiB is 413; `Content-Length: 1000` with 500 bytes delivered is **400**, and so is a stream that delivers more than it declared **under a declared length below 64 KiB** (a 1,000,000-byte stream under a declared 500), with no field parsed, nothing graded or stored, no change to any table or to the clock row, and the draft kept; the check reads `request.content_length` and not the raw header. **Edges, pinned as they behave:** at a declared length of **exactly 65,536** a stream that delivers more (70,000 bytes) is **200**, because the read stops at the declared length: the test asserts that the parsed bytes equal the declared bytes and that nothing beyond them is graded or stored, and does not assert 400. A malformed `Content-Length` is `0`, not `None`: with a body delivered it is 400 with nothing parsed; with none it reaches the `empty` outcome and nothing is stored (Gunicorn refuses it before the application, so this one is driven at WSGI level only). Empty refused; expired and abandoned refused with no answer rows; scores equal the persisted rows; weights per part; ordered and order-independent cases; a changed question after start never changes the saved score; **changing the blueprint slots after start changes neither that attempt's grading nor its maximum**; adding an id to the stimulus list after start does not drop an item of a running attempt.
- **Time.** At the deadline minus 1 s, at the deadline, at the cutoff minus 1 s, at the cutoff (exclusive), always against the **stored** cutoff. **Constant:** the same stored row at the same `now` has the same state with `SUBMIT_GRACE_SECONDS` at 60 and at 120. With `lifecycle_time`: clock regression, step, unsynchronised, reboot, suspect state give 503 and write no C3 row, and reads show persisted state. **Admit:** after a C3 write, moving the clock back is refused (no 9,000 s remaining); a read-only outcome leaves the high-water mark unchanged. **Before recovery, two cases.** (1) A forward-stamped row with the clock corrected and no recovery yet (a forward fault of **more than 60 s** driven with `lifecycle_time`, a start admitted on the ahead clock, then the wall clock corrected, the test staying on the **same boot**): every writing request is 503, no answer row is stored, and, while the clock row is usable, the read state is **not** `future-start`, because `admit()` pinned `high_water_at` at `started_at`. (2) A row made inconsistent by a fixture, or by a recovery without the marking, so that its `started_at` is later than lifecycle `now`: a submit is refused with nothing graded and nothing written, and the next start abandons it; this is a defense for an inconsistent row and is not claimed to last, nor to be reachable through the real start and clock. **Recovery (C3.2), all with the real `clock-recover` through the CLI entry on a scratch database, not a hand-written update:** (1) a 6 h forward fault, recovered at +10 minutes, with **no POST until real time passes the stamp**: the submit is refused as `abandoned`, with no answer rows; (2) a 1 h forward fault, recovered at +2 h (the row was never future-stamped): the submit is refused, with no answer rows; (3) in both cases the next start creates a new attempt if the blueprint and pools pass; (4) the clock state stays `ok`, assignment holds, retention floors and the high-water mark are as without a C3 row (compare with the same recovery on a database that has no C3 row), and a later assignment write is not blocked; (5) a recovery with no open C3 row writes no C3 row, and rows that are already submitted, expired or abandoned are not touched; (6) `clock-inspect` writes nothing, prints only the count, and that count equals the rows `clock-recover` then marks. The same cases are run against a recovery with and without a declared `--suspect-from`/`--suspect-to`, to pin that the marking does not depend on it. **Known limitation, characterized and not guaranteed (C3.2):** a start is admitted on a clock that is 1 h ahead and reports synchronised (the first lifecycle write of a boot); the clock is corrected with no lifecycle transaction between the correction and the reboot; a reboot is simulated (a new boot identity); at the next transaction the wall clock is within the 5 s regression tolerance of the high-water mark. The test records that **no fault is recorded, the clock stays `ok`, no recovery is prompted or run, and a submit is saved** at 8,400 s of true elapsed time against 5,400 s (reviewer's prototype figures), and that the same correction **without** the reboot is refused 503 with the clock `suspect` (`clock_regression` while the wall clock is more than 5 s behind the mark, otherwise `clock_step`). A second and third attempt started on the same boot before the correction are also saved past 5,400 s (7,800 and 7,200 s in the reviewer's reproduction); the same steps with the next transaction before the wall clock is within the tolerance of the mark are refused `clock_regression`. It is named as a known limitation of the design, so it is changed deliberately when separate clock-layer work closes it, and nobody reads it as a guarantee. **Schema:** the commands refuse a database with 027 pending (exit 2, nothing written), as `tests/test_lifecycle_operator.py:130,135` already pin for the existing commands (pending and unshipped migrations). All with no state change on any GET (digest of every non-canonical table and the clock row before and after, including a GET past the deadline).
- **Client (C3.5).** Markup tests for the data attributes, the draft scope string, the field names and the clearing call on the result page and the expired notice; manual browser acceptance for each case of §6.8, recorded in that PR, including the suspend across the deadline and the cutoff, the hidden tab, the refused and redirected submit keeping the draft, a draft of another attempt or owner not restored, and JavaScript disabled (manual submit).
- **Access.** Signed-out redirects write nothing; cross-origin POST is 403 before any write; another account, a teacher and an admin get 404 on attempt and result; an open, expired or abandoned attempt has no result; no correct answer in any attempt page or answer row.
