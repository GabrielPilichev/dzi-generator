# Test matrix for the future updater PR

Status: scope for the B4 updater implementation PR. It is adopted only with a READY independent review of these exact bytes. The review verdict and the SHA256 of each file are recorded outside these files, in the review handoff, its evidence manifest and the PR description. Every command, flag, exit code and report field is proposed until the implementation PR is reviewed.

Normative annex of the [scope](canonical-content-updater-scope.md); the algorithm and the fixed refusal codes are in the [implementation map](canonical-content-updater-implementation-map.md), the review decisions in the [decisions annex](canonical-content-updater-decisions.md). Nothing in this matrix was run when it was written; it is the acceptance plan for temporary databases.

Fixtures (E): `tests/update_canonical_fixtures.py`, standard library only. A synthetic **mini canonical** database: `canonical_load.migrated_empty_database` plus a few explicit-id rows in every one of the 27 canonical tables (2 curricula, sections and topics, 4 questions with options and a subquestion, one exam with 3 tasks, task links, practical task and resources, assets and links of each owner type, blueprint and slots, QTA, TSA, aliases, events), then `canonical_export.export_database` to produce the **preimage** `P`; a clone plus synthetic additions plus an export gives the **source** `S`. It includes a deliberate non-id duplicate pair of questions (a stand-in for 371/393). Runtime and operational fixtures: direct inserts (users, TOTP, identities, profiles, pending registrations, recoveries, ledgers) and the `tests/runtime_fixtures.py` helpers (standard library: `json`, `sqlite3`). A `with_real_canonical` fixture builds one module-level template with `canonical_load.rebuild_for_parity` of the tracked `data/canonical`, for exactly the control in group A. Every database is a temporary file; none reads `data/questions.db`: every new test module installs the replacement guard of scope section 2 item 5 (a patched `sqlite3.connect` that fails on `tests.runtime_db_guard.RUNTIME_DB`, by path or `samefile`). The helpers `file_bytes_digest`, `db_snapshot(conn)` (all-table dump with storage classes) and `tree_listing(dir)` support the assertions. The tool's test seam also takes keyword-only `migrations_dir` (default `ct.MIGRATIONS_DIR`) and the `after_pin` hook; neither is reachable from the CLI.

Every refusal case asserts: the exit code, the status and run-level code of implementation map section 12 (and, for `plan_conflicts`, the row or reference code), no path or exception text in the output, and the database's logical snapshot (`db_snapshot`, every table with storage classes) identical before and after. For refusals before the target is opened, and for every rollback-journal fixture, it also asserts the directory listing and the database file bytes unchanged. For WAL fixtures refused after opening, there is no assertion on sidecar presence or file bytes, because SQLite itself may create or remove `-wal` and `-shm` (scope section 4).

Each group lists positive controls (+) and negative cases (−). The matrix has **74 numbered cases** in 11 groups A-K plus the **9 sub-cases** 12a-12e, 41a and 67a-67c (83 case headings in all); several cases carry further sub-clauses. No case needs a network, server or real data. Behaviors that the sources do not prove are **expectations**, listed in implementation map section 13; the cases that depend on one say so and settle it.

## A. Baseline no-op and first apply
1. + `S == P ==` tracked `data/canonical` against a database built from it (real template): dry run exit 0 `no_change`, zero inserts, the historical identical non-id pairs 371/393 and 659/681 present and **not** refused; apply with that plan's hash exits 0 with an empty write footprint (a connect and statement spy shows no `BEGIN IMMEDIATE` and no COMMIT; database bytes identical, rollback-journal fixture).
2. + Mini fixture, `S` adds new rows in many tables: dry run lists actions, hash printed, db unchanged byte-for-byte (rollback-journal).
3. + Apply with the dry run's hash: exit 0; after-state equals `T ∪ candidates` exactly; every sequence entry equals its expected value; receipt text present, `COMMITTED`.
4. + Repeat the **old** token: exit 2 (stale), nothing written. A fresh dry run: `no_change`, exit 0, new hash; apply with it exits 0.
5. − Dry run without `--preimage`: no hash, status incomplete, exit 1; `--apply` without preimage or token: exit 1; token without `--apply`: exit 1 (usage error maps to 1, never argparse's 2).
6. + Report determinism: two dry runs give byte-identical output; JSON and text carry the same numbers.

## B. Identity, ids and sequences
7. + Explicit stable ids above target max and sequence inserted verbatim; no remap.
8. − Candidate id equal to a target-only row's id with different content: `value_differs`.
9. − Candidate id ≤ target max id; ≤ target stored sequence while the row is absent (gap id): `id_not_above_high_water`.
10. − Lowered sequence: target sequence reduced below the preimage's recorded value: `sequence_below_preimage`; a missing target entry counts as 0 and is below a recorded positive value.
11. − Id ≤ preimage max/sequence but absent from the target and the preimage: refused.
12. + **Sequence-only plan:** every source row is identical, and the target's canonical sequence is below the manifest but at or above the preimage.
    - The dry run lists sequence items only and prints a hash.
    - Apply with that hash takes `BEGIN IMMEDIATE`, raises the entry to the manifest value and commits. Exit 0. Non-canonical entries are unchanged.
    - A table whose manifest sequence is null is untouched.
    - Cover both forms: an existing entry (`UPDATE`) and an absent entry (`INSERT`).
12a. + **Empty footprint:** identical rows, and every sequence at or above the manifest. Dry run `no_change`. Apply with its hash exits 0, and a connect and statement spy shows that no `BEGIN IMMEDIATE` and no COMMIT ran.
12b. − **Failure after the sequence write:** sequence-only plan, with the hook raising after `apply_sequence` and before COMMIT. Exit 3, and the entry equals `pre`.
    - The restore lock found under the write lock **before** the first canonical write: exit 1, and the entry equals `pre`.
    - The restore lock found after the first canonical write: exit 3.
12c. + **COMMIT error, probe shows the raise:** sequence-only plan, injected COMMIT error after a real COMMIT. The probe sees `E`, so exit 4 with the "COMMITTED … visible to a fresh connection" wording.
12d. + **COMMIT error, probe shows the pre-state:** injected COMMIT error before applying, with the rollback confirmed. The probe sees `pre`, so exit 3, or exit 2 when the error is busy.
12e. + **COMMIT error, outcome unknown:**
    - The probe connection fails to open: exit 5.
    - The probe sees a mixed footprint (one sequence entry at `E`, another at `pre`; or a candidate row present while its table's sequence entry is at `pre`; or an entry at neither value): exit 5.
    - The wording says the outcome is unknown and the plan must not be retried.
13. + Composite and no-id tables (`assessment_event_sections`, `topic_classes`, `topic_prerequisites`, `exam_task_questions`, `practical_tasks`): a candidate is inserted by its full key; no id or sequence rule is applied (including `practical_tasks.task_id`, which the reference schema does not mark AUTOINCREMENT although its manifest `max_id` is non-null); identical is a no-op; a differing non-key column is `value_differs`; absent but in the preimage is `deleted_in_target`.
14. − NULL/key typing: NULL pk, float or string in an INTEGER pk, id `true`, id > 2^63-1: refused with fixed codes.
15. + Natural key with a NULL part (questions with NULL `source_number`): no key collision; the non-id guard decides.
16. − Natural key present under another id (`topic_slug`, `(source_exam, source_number)`, `(question_id, option_letter)`): `unique_key_exists`.
17. − Declared unique keys that are not natural keys: `curriculum_modules.module_number`, `exams.sha256`, `lessons(section_id,title_bg)`, partial `module_slug`: refused before any write; candidate against candidate: `unique_key_in_source_twice`. − A fixture migrations directory (through the `migrations_dir` seam) whose canonical table has a unique index with an expression column, a predicate other than `IS NOT NULL` terms over its key columns, or a non-BINARY collation: `unsupported_unique_index`.
18. − Non-id duplicate guard: a candidate question identical except `id` to an existing one: `duplicate_content`; candidate against candidate refused; a difference only in a timestamp column does **not** make the pair a duplicate (every non-id column is compared); the same pair when **both already exist and are identical**: no-op (positive control for "insert candidates only"); a table whose primary key is not `["id"]` is never subject to the guard.
19. − Differing existing values: text, `created_at` timestamp, approval flag (`is_ai_generated`, `quality_score`), `is_correct`: each `value_differs`; no partial update of other rows.
20. − `1` against `1.0` in a REAL column and in an INTEGER column: the source line differs from the target line, so `value_differs`; a source whose int is rewritten to a float by column affinity on insert passes the dry run (no prediction, implementation map section 13) and is refused by the post-insert check before COMMIT: exit 3, rolled back, nothing persisted.
21. − Absent in target but in preimage (`deleted_in_target`); in preimage but removed from source (`removed_in_source`); both refuse the whole plan, nothing applied.
22. + Target-only rows kept and reported (bounded list), including a target-only row that equals no source row; − a target-only row colliding with a candidate's unique key: refused.

## C. Source, preimage, schema, migration, classification
23. − Source: bad `format` or `format_version`; bad per-file sha256; wrong row count; non-normalized line; BOM; CR; missing final newline; duplicate key; missing or extra file; extra directory entry; symlinked file; oversized file; manifest classification differs; manifest `sqlite_sequence` below max id; manifest migration level older or newer than the repository's; manifest `primary_key` or `autoincrement` differs from the pinned reference schema (including an AUTOINCREMENT table declared `autoincrement: false`, which must not skip the high-water rule).
24. − Preimage: tampered hash, different columns, different canonical table set, newer than the source's migration list, manifest `primary_key` or `autoincrement` differing from the pinned schema; + a preimage with an **older but prefix** migration list and an added non-canonical table is accepted.
25. + Source pinning: mutate the source file after the tool read it (the `after_pin` hook): the run uses the pinned bytes and reports their hash; the copy re-hash detects tampering of the private copy (simulated) and aborts (exit 1 before the first canonical write, exit 3 after).
26. − Target schema: pending migration (row removed from `schema_migrations`), unknown applied filename, middle migration missing while the last is present, extra column, changed CHECK, missing index, extra unclassified table, classified table missing, **trigger** (even a no-op one), view, `PRAGMA quick_check` failure, pre-existing foreign-key violation. + A differing `applied_at` alone does not change the plan hash.
27. − Migration identity: a repository migration file changed against the manifest list (pinned copy, through the `migrations_dir` seam) is refused; the tool never runs a migration on the target (connect spy: every `sqlite3.connect` path is the target URI, or lies under a directory created during the run by `tempfile`: the tool's `mkdtemp`, or `canonical_export.reference_columns`' `learnpilot-reference-*`, src/canonical_export.py:54-60; never a path that resolves to the target outside its `mode=rw` URI, and never `tests.runtime_db_guard.RUNTIME_DB`; `apply_migrations` never receives the target). + Two runs in one process with different pinned migration copies get independent reference schemas (no stale `reference_columns` cache).
28. − Missing target: `--db` absent, a directory, a dangling symlink, a symlink to a valid database (symlinked final component): exit 1 before any SQLite call; nothing created: directory listing and file bytes unchanged (no database, `-wal`, `-shm` or `-journal`). + A database reached through a symlinked parent directory is accepted and opened by its resolved path.
29. − `--source` or `--preimage` missing, not a directory, or a symlink: exit 1; the source is never modified (file hashes before/after).

## D. Preservation (populated target)
30. + Populated target (accounts of all three roles, TOTP credential + recovery codes, identities, profiles, teacher subjects, pending registration, password recovery, send ledger, registration control, lifecycle clock, assignments with plans and tokens, attempts with answers/text answers/practical submissions + files, assignment creations, generated exams, login throttle, OIDC consumed tx, note links, obsidian notes, scrape log): after apply, every non-canonical table count and digest unchanged; `sqlite_sequence` entries of non-canonical tables identical.
31. + Value-class handling: a BLOB stored in a TEXT-affinity column, invalid-UTF-8 text, `1`, `1.0` and `'1'` as distinct rows, `-0.0`, empty string against NULL, WITHOUT ROWID tables, duplicate identical rows: the digest differs when any one changes (mutation checks through the hook) and is stable otherwise; the digest does not depend on row order (the same rows inserted in two orders digest equal); a connection-wide `text_factory` is never set.
32. − Injected corruption: a hook updates one runtime row, deletes one, adds one (inside the lock before COMMIT): each detected, rolled back, exit 3, database snapshot equal to pre-state. Same for one canonical row changed, a sequence lowered, a non-canonical sequence entry added.
33. + Resulting-state validation uses the union: a target with extra canonical rows and higher sequences than the source applies and validates (not fresh-build counts).
34. + Authorizer positive controls: a statement injected through the hook is denied, proving the guard is live. Read phase: `INSERT`, `UPDATE`, `DELETE`, `PRAGMA journal_mode=WAL` denied; the allowlisted reads work. Write phase: `INSERT` into a canonical table and `INSERT` and `UPDATE` of `sqlite_sequence` allowed; `UPDATE users`, `INSERT` into `users`, any `DELETE`, any `DROP` or `CREATE` denied. A statement spy shows the transition order: read `ROLLBACK`, authorizer removed, `query_only=OFF`, write authorizer installed, then `BEGIN IMMEDIATE`. The digests would also catch a leak.

## H. Concurrency, locks, WAL and rollback-journal
53. + WAL target with a writer holding an open write transaction: dry run succeeds, sees the pre-commit state, writes nothing logically (row digests equal; sidecars allowed).
54. + WAL snapshot consistency: a writer commits between two table reads (hook `after_table_read`): the plan equals the pre-write snapshot for every table (one read transaction).
55. − WAL target, a writer holds `BEGIN IMMEDIATE`: apply waits the bounded timeout, then exit 2 within a tight tolerance; nothing written. The same outcome with `sqlite_errorcode` made unavailable on the exception (message fallback of implementation map section 4).
56. + Rollback-journal target: a dry run succeeds next to a connection that holds `BEGIN IMMEDIATE` without having modified a page (no `-journal`, checked by the test). − The same, after that writer has executed an `UPDATE` (a `-journal` exists, an expectation the test settles): refused, exit 1, never opened. − With `BEGIN EXCLUSIVE` held and no `-journal`: exit 2 within the timeout.
57. + After a dry run returns, no read lock remains: another connection can `BEGIN IMMEDIATE` and COMMIT at once (rollback-journal fixture).
58. − Stale plan: a canonical row is inserted by another connection between P1 and P2 (hook `after_read_phase`): exit 2, nothing written. + A **runtime** row inserted in that window: not stale, applied, new row preserved, digests taken under the lock.
59. − Stale at P1: target changed after the dry run: exit 2 before any write lock is taken (assert via a second connection that can still write).
60. − Restore lock: present before the run (dry run and apply, exit 1, the target never opened: the connect spy sees no connect to it); present only next to the absolute given path, or only next to the resolved path (a given path with `..` components through a symlinked directory, where the lexical and resolved parents differ): each refused; created while apply waits for `BEGIN IMMEDIATE` (a thread holds the write lock, creates `restore-in-progress`, releases): refused under the lock before the first canonical write, exit 1, nothing written; created between inserts and COMMIT (hook): rolled back, exit 3, nothing persisted; a *file* named `restore-in-progress` counts (`lexists`).
61. + Two apply processes with the same token race: exactly one commits, the other exits 2.
62. − Any `<db>-journal` present (empty file, PERSIST-style header, or a real hot journal): refused before opening; the connect spy shows no `sqlite3.connect` to the target.

## I. Failure injection and COMMIT outcome
63. Hook raises after the first table, after the last insert, after `apply_sequence`, before COMMIT: exit 3, snapshot equal to the pre-state, no sidecar left in a rollback-journal fixture, connection closed.
64. − SQLite constraint violation under the lock (an index the pre-check cannot see, injected by schema-compatible trigger-free means such as a CHECK edge): rolled back, exit 3.
65. + Connection factory: COMMIT fails **before** applying (raise, transaction still open): `ROLLBACK`, the probe finds every write-footprint item at its pre-state, exit 3; with `SQLITE_BUSY`, exit 2 (also with `sqlite_errorcode` unavailable).
66. + COMMIT executes then raises: the probe finds every write-footprint item at its expected post-state, reported committed; the message names the COMMIT error and says "COMMITTED … visible to a fresh connection"; exit 4; no "rolled back", no "durable", no "this run committed". A second applier with the same token that commits after the first run's failed COMMIT leaves the first run's report unchanged (exit 4, the same wording).
67. + COMMIT raises and the probe connection also fails (the injected `connect` raises for the probe): exit 5, text says the outcome is unknown and not to retry.
67a. + The probe sees a `-journal` after the injected COMMIT error: exit 5, the probe never opens.
67b. + `ROLLBACK` raises "no transaction is active" (the injected COMMIT error ended the transaction) and the probe finds no footprint item at its post-state: exit 3, wording "not committed".
67c. + Probe result mixed (an injected probe connection returning a partial view): exit 5.
68. + Receipt stream raises after a real COMMIT: exit 4; database contains the rows; wording says COMMITTED and not rolled back.
69. + Pre-write failures never use 3/4/5: unreadable source (1), restore lock under the lock before the first canonical write (1), busy (2), stale (2).
70. + No temporary directory remains after success, refusal and failure; pinned copies and reference databases removed.

## J. Static guards on the module source
71. The module source contains none of these SQL and API forms: `DELETE\s+FROM`, `INSERT\s+OR\s+REPLACE`, `REPLACE\s+INTO`, `ON\s+CONFLICT`, `executescript`, `immutable=1`, `journal_mode\s*=`, `shutil.copy*`, `os.environ`, `getenv`, `subprocess`, `socket` and `urllib` and `http` imports, `app.run`, the string `data/questions.db`, `DZI_RECOVER`; it imports only the allowed modules; `manage_migrations.apply_migrations` is not referenced with a non-temporary path (an AST check that its only call receives the reference-path variable). Bare words are not matched, so `sqlite3.SQLITE_DELETE` and prose are accepted.
72. `sqlite3.connect` spy (the pattern of tests/test_build_database.py:170-204, a patched `sqlite3.connect`, not an audit hook): only the target URI, or a path under a directory created during the run by `tempfile` (the tool's `mkdtemp`, or `canonical_export.reference_columns`' `learnpilot-reference-*`); never a path that resolves to the target outside its `mode=rw` URI; never `tests.runtime_db_guard.RUNTIME_DB`. The replacement guard of scope section 2 item 5 is exercised: a deliberate attempt to connect to the runtime database path makes it fail, and no test module opens `data/questions.db`.
