## 1. Module outline

One module, standard library only. Imports `src.canonical_tables as ct`, `src.canonical_export as export`, `src.canonical_load` (only `apply_sequence`), `src.canonical_parity as parity` (only `embedded_reference_problems`), `src.schema_introspection`, `src.manage_migrations` (only against a throwaway reference database), `web.services.lifecycle` (only `restore_lock_path` and `restore_lock_present`; a stdlib-only module, imported the same way at src/backup_application.py:38; `web/` has no `__init__.py`, so it is a namespace package: run as `python3 -m` from the repository root). The module must not read environment variables, mention `data/questions.db`, or contain `DZI_RECOVER` or `RECOVERY_ENABLED|ACTIVATION` (tests/test_recovery_production.py:104-110).

Sections: constants, vocabulary and exit codes (section 12); `pin_directory` and `pin_migrations`; `validate_source` and `validate_preimage`; `reference_schema` (columns, keys, autoincrement, unique indexes, shapes, load order from the pinned migrations); target open, lock and compatibility; `read_target_state`; `extract_references`; `build_plan` (classification, unique checks, history rules, file references, write footprint); `preservation` digests; `apply_plan`; `commit_probe`; `render_report` and redaction; `run()` with an injectable seam and `main()`. Expected size 1,000-1,500 lines.

Test seam (E): `run(argv, *, out, err, hooks=None, connect=sqlite3.connect, migrations_dir=ct.MIGRATIONS_DIR)`. `hooks` has optional callables `after_pin()`, `after_read_phase(conn)`, `after_table_read(table)`, `after_lock(conn)`, `after_insert(table)`, `after_sequence(table)`, `before_commit(conn)`. `migrations_dir` lets a test pin a fixture migration set; neither it nor a hook is reachable from the CLI. `connect` may return a `sqlite3.Connection` subclass (factory) so tests can fail or delay a specific `COMMIT` without patching `sqlite3` globally. **Every** target connection, including the post-COMMIT probe connection (section 9 step 4), is opened through `connect`.

## 3. Pinning and validation (design section 5: "source files are read once")

1. `os.scandir` the source directory without following links; accept only regular files named `manifest.json` or `<canonical table>.jsonl` (27 tables); refuse symlinks, non-regular files, extra files, files over 64 MiB, more than 512 MiB total.
2. Read each file **once** (`O_NOFOLLOW`), hash the bytes, write to a fresh `mkdtemp` 0700 directory (files 0600). Same for the preimage directory and for `ct.MIGRATIONS_DIR/*.sql` (26 files today; `migration_filenames` globs `*.sql` regular files, src/manage_migrations.py:76-79). Record per-file sha256. Every pinned directory is a new unique name; a fixed name would let the `lru_cache` in `reference_columns` return a stale answer.
3. All later reads (`check_directory`, `read_table_rows`, the reference-schema build) use the copies. Re-hash the copies after planning and immediately before COMMIT; a difference aborts as an internal error (exit 3 after the first canonical write, otherwise 1).
4. Source: `check_directory(src_copy, mig_copy)` must return `[]`. In addition:
   - the manifest `canonical_tables` equals `canonical_load_order` of the reference database (as `load_canonical` does against the target, src/canonical_load.py:83);
   - every int is in 64-bit range, every primary-key component has the declared type, no primary key is NULL;
   - for every canonical table, the manifest entry's `primary_key` and `autoincrement` equal `ct.primary_key_columns` and `ct.is_autoincrement` of the **pinned-migration reference database** that the tool builds itself. `check_directory` does not check them (src/canonical_export.py:183-208). A mismatch refuses the source. Every key and every id rule below is derived from that reference schema; a manifest declaration never bypasses a high-water rule.
5. Preimage (E): local validation with the same strictness:
   - format and version; per-file count and digest equal to its own manifest via `ct.file_digest`; `read_table_rows` strictness; duplicate-key, `max_id` and sequence consistency as in `check_directory`, computed against the reference schema's keys;
   - the canonical table set equal to the source's; per table `columns` equal to the source's, and `primary_key` and `autoincrement` equal to the pinned reference schema (the same check as step 4);
   - the preimage migration list is a prefix of the repository list.
   Classification and migration-level equality are deliberately not required.
6. Identity facts in the report: manifest sha256, combined per-file hash, migration level, repository migration-list hash (filename plus file hash).

## 4. Target access

- **Preflight order** (E; design section 2 "before reading the target"): arguments, then pin and validate source, preimage and migrations (section 3), then the restore lock for the absolute given path **and** the resolved path (`lifecycle.restore_lock_path` of each), then `os.lstat` of the given path must be a regular file (a symlinked final component, a directory or a missing path is refused), then the journal check, then open. Nothing reads the target before the restore-lock check. A refusal before open leaves the directory listing unchanged: no database, `-wal`, `-shm` or `-journal` appears. (The reference databases of validation live in the temporary directory, not beside the target.)
- **Journal check** (E): refuse (exit 1, before opening) whenever `os.path.lexists("<resolved db path>-journal")`, hot or not. Hotness cannot be decided without opening and locking the file, and production uses WAL (docs/DEPLOYMENT.md:206-211). This is best effort with a time-of-check window: a journal that appears after the check is handled by SQLite itself. Whether a rollback-journal writer that has modified a page keeps a `-journal` file is an **expectation** that the tests check.
- **Connection**: `sqlite3.connect(<resolved path as_uri>+'?mode=rw', uri=True, timeout=busy_ms/1000, isolation_level=None)` through the injectable `connect`; `PRAGMA foreign_keys=ON` while no transaction is open and before any authorizer is installed; never `PRAGMA journal_mode=` or `synchronous` setters. `mode=rw` never creates a missing file (src/backup_sqlite.py:137).
- **Dry-run and read phase**: `PRAGMA query_only=ON`; then the read authorizer (below); explicit `BEGIN`; all reads in that one transaction (one WAL snapshot); `ROLLBACK` at the end. Logical writes: none. A WAL database may gain `-wal` and `-shm`, and the last-close checkpoint may rewrite main-file bytes without changing any row (design section 6; whether the checkpoint runs while `query_only` is on is an **expectation**). Byte and listing equality is therefore asserted only for rollback-journal fixtures and for refusals before the target is opened; for WAL fixtures only the logical snapshot is compared. In rollback-journal mode the read transaction holds SHARED and delays other writers' COMMIT, so it is kept short and ended before any write phase; production's WAL mode does not block writers.
- **Authorizer allowlists** (E, defense in depth; the digest checks remain the contract if a SQLite build disagrees):
  - Read phase: `SQLITE_SELECT`, `SQLITE_READ`, `SQLITE_FUNCTION`, `SQLITE_TRANSACTION`, and `SQLITE_PRAGMA` limited to `table_info`, `index_list`, `index_xinfo`, `foreign_key_list`, `foreign_key_check`, `quick_check` and `journal_mode` with no argument. Anything else is denied. A further allowance must be read-only (never a write, DDL or ATTACH code) and is named in the module with the reason a test showed it necessary.
  - Write phase: the read allowances plus `SQLITE_INSERT` on canonical tables and on `sqlite_sequence`, and `SQLITE_UPDATE` on `sqlite_sequence` only (`apply_sequence` issues both forms, src/canonical_load.py:61-63). Everything else is denied: `DELETE`, `DROP`, `CREATE`, `ALTER`, `ATTACH`, `ANALYZE`, `REINDEX`, any other `UPDATE` or `INSERT`. Whether SQLite consults the authorizer for AUTOINCREMENT's implicit `sqlite_sequence` write is an **expectation**; the two allowances cover both outcomes.
- **Transition to the write phase** (before `BEGIN IMMEDIATE`, in this order): `ROLLBACK` the read transaction, remove the read authorizer, `PRAGMA query_only=OFF`, install the write-phase authorizer, then `BEGIN IMMEDIATE` with the bounded timeout. `SQLITE_BUSY` or `SQLITE_LOCKED` beyond the timeout means exit 2. Classify with `getattr(exc, "sqlite_errorcode", None)` where the interpreter provides it (3.11 and later) and with an exact message match otherwise; the message fallback is covered by a test (the repository already uses the `getattr` form, web/services/oidc_consumption.py:209, and documents the older-Python fallback, docs/DEPLOYMENT.md:2224-2228). No project minimum is raised and no interpreter capability is assumed.
- **Compatibility** (any failure refuses, exit 1, nothing read further): `classification_problems` empty; `[filename ORDER BY filename]` equals the pinned migration list exactly (pending or unknown refused, never applied; the applied filenames are compared, `applied_at` is never hashed or compared); `table_shape` of every user table equals the reference; `sqlite_master` has no trigger and no view; manifest load order equals `ct.canonical_load_order(target)`; `PRAGMA quick_check` = `ok`; `PRAGMA foreign_key_check` empty.
- **Concurrency statement**: the tool is designed for concurrent writers (write lock, replan under the lock, stale refusal; WAL does not block readers). It does not detect a running service. The write lock is held for the whole replan, insert and validation phase, which delays service writers by an amount that is not measured here.

## 5. Plan identity and phases

`plan_sha256` = sha256 of compact sorted-key JSON of: plan-format version; source identity; preimage identity; repository migration identity; the target's applied migration **filenames**; target schema identity (sha256 of `table_shape` JSON for every table plus the non-`sqlite_%` object inventory); per canonical table `(count, ct.table_digest)` of the **target pre-state**; target canonical sequences; source manifest sequences; the sorted action list `(table, key, sha256(normalized line))` for candidate rows **and** `(table, pre, E)` for every sequence item. Not hashed: runtime and operational digests, journal mode, timestamps, paths.

**Write footprint** (E; one definition, used by the phases, the exit codes and the probe). The footprint is:

- (a) the candidate rows, each with its key and normalized line;
- (b) every canonical `sqlite_sequence` entry whose expected post-state `E = max(pre, manifest sqlite_sequence)` differs from its exact pre-state `pre`. `pre` is the integer or "absent"; for the comparison "absent" counts as 0, and `E` is recorded as an integer. A table whose manifest sequence is null contributes no item. Part (b) includes entries that AUTOINCREMENT itself raises while inserting candidates (it raises to the largest inserted id, at most the manifest value, which `check_directory` validates, src/canonical_export.py:204-206).

If the footprint is empty the plan is "no change". A plan with only sequence items is a writing plan and follows the full P2 path.

Phases:

- P1 (dry run and apply): consistent read, plan P1. A dry run prints it. Apply compares it to `--expect-plan-sha256`: a difference exits 2 before any write lock is taken.
- P2 (apply only, when the P1 footprint is non-empty): close the read transaction, make the transition of section 4, `BEGIN IMMEDIATE`, recheck the restore lock (exit 1), recheck schema, migrations, triggers and classification, recompute the whole plan inside the lock, compare it to the token (a difference means `ROLLBACK` and exit 2). An empty footprint never takes the write lock and never runs COMMIT (exit 0, "no change").
- Runtime writes between P1 and P2 do not stale the plan (positive control) but are re-gated and re-digested under the lock.

## 6. Row classification (per canonical table, manifest order)

Source `S`, preimage `P` and target `T` are keyed by the **reference schema's** primary key (never the manifest's declaration). Key types: int for INTEGER primary-key columns, str for TEXT (for example `exam_task_questions.role`), anything else `invalid_key_type`; a NULL component is `null_primary_key`. Identical means `ct.serialize_row` lines equal, so `1` and `1.0` differ (design section 3; SQLite REAL affinity can rewrite `1` to `1.0` on insert, and the post-insert line check refuses that source before COMMIT).

For each `s` in S:

1. `s.key in T`: equal lines mean `identical`; otherwise `value_differs` (list differing column names only).
2. Absent from T:
   - `s.key in P` means `deleted_in_target`.
   - Otherwise it is a **candidate**. For tables whose reference schema says AUTOINCREMENT only: `id` must exceed `max(T.max_id, T.stored_sequence, P.max_id, P.sqlite_sequence)` (a missing sequence entry counts as 0 in every comparison), else `id_not_above_high_water` (src/canonical_tables.py:256-271). Tables without an AUTOINCREMENT id (`assessment_event_sections`, `topic_classes`, `topic_prerequisites`, `exam_task_questions`, `practical_tasks`) skip this rule and use the full key.

For each `p` in P not in S: `removed_in_source`. For each `t` in T not in S and not in P: `target_only` (kept; counted; at most 20 keys listed).

Sequences: if the target's stored sequence (absent counts as 0) is below the preimage's recorded sequence for an AUTOINCREMENT table, the plan is refused with `sequence_below_preimage` (a lowered sequence). Otherwise sequence items are planned as in section 5, and `apply_sequence` runs only for them.

Candidate-only checks:

- **Declared unique keys** (E): every UNIQUE, primary-key and unique-index key of the table in the pinned reference schema (`PRAGMA index_list` and `index_xinfo`), not only `NATURAL_KEYS`: candidate against the target's other rows and candidate against candidate, giving `unique_key_exists` and `unique_key_in_source_twice`. NULL-containing keys never collide (SQLite semantics, matched by src/canonical_export.py:211). Supported partial-index predicates are exactly the forms present today: `<key> IS NOT NULL` (`idx_curriculum_modules_slug`, web/migrations/000_baseline.sql:383-385) and `<key1> IS NOT NULL AND <key2> IS NOT NULL` (`uniq_questions_source_exam_number`, web/migrations/004_dzi_safety_constraints.sql:3-5). Because a NULL-containing key never collides, no predicate evaluator is needed. Any other partial-index predicate, any expression column, or any non-BINARY collation in a unique index of a canonical table refuses the plan with `unsupported_unique_index`; no `COLLATE` appears in any migration today. Needed because constraints exist beyond `NATURAL_KEYS`, for example `curriculum_modules UNIQUE(module_number)` (web/migrations/000_baseline.sql:58), `exams UNIQUE(subject,level,year,session,variant)` and `sha256 UNIQUE` (web/migrations/000_baseline.sql:221, 214), `lessons UNIQUE(section_id,title_bg)` against the natural key `(section_id, lesson_number)` (web/migrations/000_baseline.sql:87 against src/canonical_tables.py:114). SQLite's constraint error under the lock is the backstop (rolled back, exit 3).
- **Non-id duplicate guard, INSERT CANDIDATES ONLY**: applies only to tables whose reference primary key is `["id"]`. Every non-id column, timestamps included, is compared (design section 3, "natural key or non-id content present under another id"): a candidate whose normalized non-id content equals any target row's under another id, or another candidate's, is `duplicate_content`. Existing canonical data has identical non-id pairs 371/393 and 659/681 (static scan of `data/canonical/questions.jsonl`), so an unchanged database yields no candidates and stays a no-op; a source containing such a pair where one member is a candidate is refused (documented consequence: it needs reviewed reconciliation).

- Id positions: the top-level value itself, every element of every list at any depth, and every value of every dict at any depth under any key. ## 8. File references (metadata only; candidates only)

Columns: `assets.local_path`, `practical_task_resources.resource_path`, `official_exam_sources.local_path`, `exams.source_file`, `questions.image_path`, `curriculum_topics.note_path`, `curriculum_areas.moc_filename`, `curriculum_modules.moc_filename`. NULL is allowed where the schema allows it.

Observed in current canonical data (static scan): no backslash, `..`, absolute or URI value; all NFC; 77 `practical_task_resources` paths contain non-ASCII (Cyrillic and spaces), 60 use `archive.zip::member`; 3 `exams.source_file` values end with `/` (`reference/aug_2023/`); `assets.local_path` under `data/reference/` or `web/static/img/`; `moc_filename` values are bare names.

Rules, mirroring `_relative_parts` (src/practical_resource_resolution.py:49-61) and `question_visual_static_filename` (web/services/question_visuals.py:20-35), but **refuse, never rewrite** (code `unsafe_file_reference`; a rewritten value would no longer equal the reviewed source line): not str, empty, leading or trailing space, control characters or NUL, backslash, leading `/` or `~`, `://`, any `:` (drive letters) other than the single `::` archive separator in `resource_path`, empty, `.` or `..` segments, non-NFC, `PurePosixPath(raw).as_posix() != raw`, length over 512. Report line: `file availability: not checked`; web code checks existence at runtime (quiz.py:985), so a missing file silently makes a new visual question ineligible: stated in the report, not verified.

## 9. Apply sequence (under the write lock)

1. **Pre-write snapshot**: per non-canonical table (every `TABLE_CLASSIFICATION` entry that is not canonical, minus `sqlite_sequence`) count plus multiset digest; `sqlite_master` inventory digest; `sqlite_sequence` map; canonical pre-state lines per table.
   Digest (E): per row, a type-tagged, length-prefixed encoding with the SQLite storage class (`typeof`) for every column, exact bytes for text and blob (text read as bytes with `CAST(column AS BLOB)` in SQL, decode-free, so invalid UTF-8 cannot crash it; never a connection-wide `text_factory`, which would break canonical reads on the same connection), IEEE-754 double bits for real (`1`, `1.0` and `'1'` differ; `-0.0` is kept), NULL. The table digest is the sha256 of the count followed by the **sorted** per-row sha256 digests: exact and independent of row order (WITHOUT ROWID tables such as `login_throttle`, web/migrations/013_login_throttle.sql, and `oidc_consumed_transactions`, web/migrations/020_oidc_consumed_transactions.sql, have no rowid, and rows that compare equal as int and real have no stable sort). Not `ct.serialize_row`, which rejects blobs and NaN (src/canonical_tables.py:196-198).
2. **First canonical write and after**: insert candidates table by table in manifest order, `INSERT INTO "t" (cols) VALUES (?...)` with explicit ids and bound parameters; identifiers validated against `^[A-Za-z_][A-Za-z0-9_]*$` and equal to the reference columns. `apply_sequence` after each table, for footprint sequence items only. A sequence-only plan executes only the sequence writes.
3. **In the same transaction, before COMMIT**: canonical after-state per table equals pre-state lines union candidate lines exactly (dict equality: nothing changed, nothing missing, nothing extra, all source rows identical); every sequence entry equals its footprint `E` or its unchanged `pre`; preservation digests equal; `foreign_key_check` empty; `quick_check` ok; `embedded_reference_problems` empty; inserted counts equal the plan; pinned copies re-hashed; restore lock rechecked. Any failure after the first canonical write means `ROLLBACK` and exit 3; a failure before it means `ROLLBACK` and exit 1, or exit 2 for a plan-hash difference (section 10).
4. **COMMIT**. If COMMIT raises:
   - (a) Record the error class and the SQLite error name. Run `ROLLBACK` once and ignore its error (it may say that no transaction is active). Record `open_txn = conn.in_transaction`, then close the connection.
   - (b) If `open_txn` is still true, exit 5.
   - (c) If `<resolved db path>-journal` exists, exit 5. The probe never opens a database that has a journal present.
   - (d) Open a fresh probe connection **through the same injectable `connect`**, with `mode=rw`, `query_only=ON` and the read authorizer. In one read transaction, read every footprint item: the candidate keys and lines, and the planned `sqlite_sequence` entries. If the probe cannot open or read, exit 5.
   - (e) If **every** footprint item is at its expected post-state (each candidate row present with an identical line, and each sequence entry equal to `E`), exit 4. The wording is "COMMITTED: the planned write footprint is visible to a fresh connection after a COMMIT error `<name>`". It never says "durable" and never says "this run committed": another applier holding the same token could have committed the same footprint after this run's COMMIT failed and released the lock, because its replan under the lock would equal the token.
   - (f) If **every** footprint item is at its exact pre-state (each candidate row absent, and each sequence entry equal to `pre`, including absent), the outcome is "not committed": exit 2 for a busy or locked COMMIT error, otherwise exit 3.
   - (g) Anything else is exit 5: a mix, a sequence entry at neither `pre` nor `E`, or a differing line.
   The footprint is never empty here, because an empty footprint never reaches COMMIT; that rules out a vacuous classification. No branch claims a rollback that was not confirmed by (b) and (f).
5. **Post-COMMIT**: print the receipt (the final report) to `out`; a failure (for example closed stdout) means exit 4, "COMMITTED, receipt not written". The receipt is not stored in the database (design section 5) and is not a history witness (PR #327 open).

## 10. Failure and exit map

| Situation | Exit | Database |
| --- | --- | --- |
| usage error, unreadable or invalid source or preimage, bad manifest, hash, format or classification, pending or unknown migration, shape mismatch, trigger or view, restore lock (before reading, or under the write lock before the first canonical write), journal present, conflicts, unsafe path, unresolved reference, missing preimage on apply, internal error before the first canonical write | 1 | untouched |
| busy beyond timeout (read or `BEGIN IMMEDIATE`) | 2 | untouched |
| plan hash differs (P1 or replan under the lock); old token after a successful apply | 2 | untouched |
| exception after the first canonical write and before COMMIT (injected, constraint error, I/O), in-transaction validation or preservation failure, restore lock found before COMMIT, pinned-copy re-hash mismatch | 3 | untouched (not committed) |
| COMMIT raised and the probe found every footprint item at its exact pre-state | 3, or 2 when the COMMIT error was busy or locked | untouched (not committed) |
| COMMIT raised and the probe found every footprint item at its expected post-state | 4 | committed (visible to a fresh connection) |
| COMMIT succeeded, receipt write failed | 4 | committed |
| COMMIT raised and the outcome is unconfirmed (probe failed, journal present, transaction still open, mixed or unexpected state) | 5 | unknown |
| dry run applicable or no change; apply committed and receipted; apply with an empty write footprint (no write lock, no COMMIT) | 0 | untouched / committed |

Rollback undoes one uncommitted transaction only; a snapshot restore (DEPLOYMENT section 17) is not this tool's remedy and discards later runtime writes (design section 5). The tool does not describe or design a backup or restore protocol.

## 11. Explicit prohibitions in the module (static-guard tests)

Static guards match SQL forms, not bare words, because `sqlite3.SQLITE_DELETE` and prose would trip a bare-word match: `DELETE\s+FROM`, `INSERT\s+OR\s+REPLACE`, `REPLACE\s+INTO`, `ON\s+CONFLICT`, `executescript`, `immutable=1`, `journal_mode\s*=`, `shutil.copy*` of a database, `os.environ` and `getenv`, `app.run`, `subprocess`, network modules, the string `data/questions.db`, and `DZI_RECOVER`. `manage_migrations` is never given the target path. `sqlite3.connect` is only ever called with the target URI or a path in a directory created during the run by `tempfile` (the tool's `mkdtemp`, or `canonical_export.reference_columns`' `learnpilot-reference-*`, src/canonical_export.py:54-60), checked by a patched-connect spy.

- `commit_error_committed`: exit 4
- `receipt_not_written`: exit 4

Counters: `identical`, `insert`, `target_only`, `conflict`, `under_existing_parent`, `questions_added_to_existing_topics`, `sequence_items`. Report status values and their exit-code mapping:
- `no_change`: exit 0, a dry run or an apply with an empty footprint;
- `planned`: exit 0, a dry run;
- `incomplete`: exit 1, a dry run without `--preimage`;
- `refused`: exit 1 or 2 before the first canonical write;
- `not_committed`: exit 3, or exit 2 after a busy or locked COMMIT error that the probe confirmed;
- `applied`: exit 0 after COMMIT, or exit 4;
- `outcome_unknown`: exit 5.

A run never reports `refused` or `applied` for exit 3 or exit 5.

## 13. Known limitations and unverified expectations

- **No dry-run affinity prediction.** A source whose value SQLite rewrites on insert through column affinity (`1` into a REAL column, `1.0` into an INTEGER column) is not predicted by the dry run. The post-insert line comparison (section 9 step 3) is the safety boundary: apply refuses before COMMIT, nothing persists, exit 3. A dry run can therefore report an applicable plan that apply refuses; a round-trip prediction was considered and is not part of this scope.
- **Expectations the future tests settle (not facts):** the WAL last-close checkpoint while `query_only` is on; whether `mode=rw` recovers a hot journal on first read (the journal refusal avoids reaching it); whether the authorizer is consulted for AUTOINCREMENT's implicit `sqlite_sequence` write; whether a rollback-journal writer that has modified a page keeps a `-journal` file; SQLite ending a transaction automatically on some COMMIT errors; whether `os.stat` raises an audit event (this scope does not rely on audit events: referenced-path access is checked with patched spies, see the test matrix).
